# Upgrading

This guide covers updating an existing installation to a newer version of the platform.

## Before You Upgrade

1. **Check the changelog.** The admin panel banner links to the GitHub release notes. Read what changed.
2. **Backup student work.**
   ```bash
   ./backup.sh
   ```
3. **Backup configuration and state.**
   ```bash
   cp config.env config.env.bak
   cp -r portal-data portal-data.bak
   ```
4. **Note the current version.**
   ```bash
   cat portal/version.json
   ```

## Upgrade Procedure

### Standard Upgrade (Minor or Patch Version)

```bash
cd ~/code-sphere

# 1. Stop the platform
./parar.sh

# 2. Pull the new code (if installed via git)
git pull

# OR extract from a release tarball:
# tar -xzf code-sphere-vX.Y.Z.tar.gz --strip-components=1

# 3. Re-generate config files
./gerar.sh

# 4. Rebuild images
docker compose build portal

# Optional: rebuild student image only if the student Dockerfile changed
docker build -f aluno.Dockerfile -t sala-aluno:latest .

# 5. Restart with new images
./iniciar.sh
```

### Major Version Upgrade (Breaking Changes)

A major version (`1.x.x` → `2.0.0`) signals breaking changes. Read the changelog carefully — it will document migration steps specific to that release.

In general, expect to:
- Re-run `./setup.sh` to reconfigure if `config.env` schema changed.
- Run a one-time migration script if data formats changed.
- Update any custom modifications you've made to the system.

## Verification After Upgrade

```bash
# 1. Confirm the version
cat portal/version.json

# 2. Confirm everything is running
docker ps | grep -E 'traefik|portal'

# 3. Confirm a test login works
# Visit /admin and log in.
# Visit / and log in as a test student.

# 4. Confirm Python and display stack work in student containers
docker exec sala_aluno01 python3 --version
docker exec sala_aluno01 python3 -c "import pygame; print('pygame ok')"
docker exec sala_aluno01 python3 -c "import pgzero; print('pgzero', pgzero.__version__)"
# Should print: pgzero 1.2.1
docker exec sala_aluno01 pgrep -a Xvfb
docker exec sala_aluno01 pgrep -a pulseaudio
# Should print the PulseAudio process line (audio do monitor)
docker exec sala_aluno01 pgrep -af "websockify 6081"
# Should print the Xvfb process line
```

## Rolling Back

If the upgrade caused problems:

```bash
cd ~/code-sphere

# 1. Stop everything
./parar.sh

# 2. Restore configuration
cp config.env.bak config.env

# 3. Check out the previous version (if using git)
git checkout v<previous-version>

# OR re-extract the previous release tarball.

# 4. Restore portal data if it was modified
# (Usually not necessary; the format rarely changes)
# rm -rf portal-data && cp -r portal-data.bak portal-data

# 5. Rebuild and restart
./gerar.sh
docker compose build portal
./iniciar.sh
```

## What Persists Across Upgrades

These are preserved automatically:
- **Student work** (`./alunos/alunoXX/workspace/`)
- **Student passwords** (`./portal-data/alunos.json`)
- **Active sessions** (`./portal-data/sessoes.json`) — though active sessions may expire if the portal restarts during their use

These get regenerated:
- `docker-compose.yml` (regenerated by `gerar.sh` from current `config.env`)
- `traefik/dynamic/routes.yml` (regenerated)

These are versioned in the repository:
- `setup.sh`, `gerar.sh`, `iniciar.sh`, `parar.sh`, `preaquecer.sh`, `backup.sh`, `url_atual.sh`
- `aluno.Dockerfile`
- `portal/` (Python code, templates, requirements)
- `vscode-defaults/settings.json`
- `version.json` (in both root and `portal/`)

## Customizations and Upgrades

If you've modified files in your installation (e.g., added a custom welcome message in the templates, or changed the student Dockerfile to install extra packages):

- Document your changes somewhere (a file in `./customizations/` or a personal git branch).
- After upgrading, reapply your changes manually.
- For frequent customizations, consider forking the repo and merging upstream periodically.

The platform doesn't have a plugin system — customizations are direct file edits, and you're responsible for keeping them aligned with upstream.

## Versioning Reference

The platform follows [Semantic Versioning](https://semver.org/):

- **PATCH** (`1.0.0` → `1.0.1`): bug fixes, no behavior change. Always safe to upgrade.
- **MINOR** (`1.0.0` → `1.1.0`): new features, backward-compatible. Safe to upgrade; new features may need configuration to enable.
- **MAJOR** (`1.0.0` → `2.0.0`): breaking changes. Read migration notes; data or config may need conversion.

The version is in `portal/version.json` along with the changelog. The admin panel reads this to display the current version and check for updates.
